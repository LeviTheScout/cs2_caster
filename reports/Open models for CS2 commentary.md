# CPU latency pushes the pick to 4B

**Use Qwen3-4B-Instruct-2507 as the primary base to fine-tune and Gemma 4 E4B as the comparison model. Qwen3-8B should move from primary to a latency reference and the GPU-fallback model.** The deciding constraint is the 2–3 s per-line budget on a CPU-only i7-13700K, not quality. A dense 8B at Q4_K_M is estimated at 9–13 tok/s on dual-channel DDR5 and 6–8 tok/s on DDR4, so a 30–45-token output (intensity token plus line) takes about 3–5 s to generate before any prompt is processed; models with about 4–4.5B active parameters run roughly twice as fast. Qwen3-4B-Instruct-2507 is the only candidate that meets every constraint at once. It runs in non-thinking mode only, so no `<think>` tags can leak into a strict output format. Qwen reports a Creative Writing v3 score of 83.5 for it, against 64.5 for Qwen3-8B with thinking off. It is a plain full-attention transformer, the simplest case for llama.cpp prompt-cache reuse, and it has easy QLoRA on a free T4, mature GGUF and Ollama support, and an Apache 2.0 licence. Gemma 4 E4B keeps its place because it costs about the same per token, comes from the family with the strongest independent record for small-model prose, and gives a real cross-family A/B test. It is also now Apache 2.0, so the project plan's licence worry no longer applies. Its open risk is whether its sliding-window attention lets the llama.cpp server reuse the cached prompt. None of the 2026 newcomers displaces either pick. Unsloth advises against QLoRA on Qwen3.5, LFM3-1.7B was five days old with unverified tooling, Nemotron 3 Nano 4B and the Liquid models use hybrid architectures whose prompt-cache behaviour is unproven, and gpt-oss-20b cannot turn its reasoning off. Every CPU speed figure here is an estimate: no trustworthy llama.cpp benchmark exists for this CPU, and DDR4 versus DDR5 alone is about a 1.7× swing in generation speed. The report therefore ends with a four-model bake-off on stock GGUFs that settles latency before any GPU time is spent.

## An 8B dense model likely needs 4–8 s per line on this CPU

**Generation speed on a CPU is set by memory bandwidth**, because each generated token streams all the active weights through RAM once. Dual-channel DDR5-5600, the fastest memory the 13700K is rated for, peaks at 89.6 GB/s. Dual-channel DDR4-3200 peaks at 51.2 GB/s, and real systems reach about 70–90% of either figure. A Q4_K_M 8B reads about 5 GB per token, which works out to **about 9–13 tok/s on DDR5 and 6–8 tok/s on DDR4**. A 4B reads about 2.5 GB and gets 17–25 and 11–16 tok/s. The closest community measurement agrees: Llama 3.1 8B at Q4_K_M runs at about **10 tok/s on an i7 with DDR5**, and only the P-cores matter ([InsiderLLM CPU-only guide](https://insiderllm.com/guides/cpu-only-llms-what-actually-works/)). At that speed an 8B spends 3–5 s generating the line alone. The project plan estimated 8–15 tok/s and 2–3 s per line once the prompt was cached, but that assumed a 25-token line and left out the cost of processing the new part of the prompt.

**Prompt processing is the larger and less certain cost.** It is limited by compute, and the 13700K has AVX2 but no AVX-512. At the slow end, gpt-oss-20b, a model with only 3.6B active parameters, processed prompts at **about 57 tok/s (pp512)** on mainline llama.cpp on a 16-core Threadripper 1950X ([Nikro, CPU-only LLM inference](https://nikro.me/articles/professional/cpu-only-llm-inference/)). At that rate an uncached 1,000-token frame would take about 17 seconds. At the fast end, a tuned Ryzen 9 9950X with DDR5-6400, running the ik_llama.cpp fork, exceeded 500 tok/s prompt processing and 30 tok/s generation on Qwen3-30B-A3B ([ubergarm discussion](https://huggingface.co/ubergarm/Qwen3-30B-A3B-GGUF/discussions/2)). The 13700K will land somewhere between, and nobody has measured where. One widely indexed benchmark claims 26.4 tok/s generation for Qwen3-8B on a 7950X. Ignore it: that rate needs more memory bandwidth than dual-channel DDR5-6000 can physically deliver ([markaicode](https://markaicode.com/benchmarks/llamacpp-tokens-per-second-benchmark/)).

**The llama.cpp server's prompt cache is what makes the budget reachable.** `cache_prompt` is on by default. The server keeps the previous request's KV cache, and "only the suffix that differs between the requests" is processed. Every response reports `tokens_cached` and `tokens_evaluated`, so cache hits can be checked, and `--cache-reuse` can recover matching chunks that are not a strict prefix ([llama.cpp server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)). If the match card and round state stay fixed at the front and only the newest events and previous lines change at the end, the prompt work per line drops from 1,000+ tokens to about 150–250. The table below combines this with the bandwidth figures. It is arithmetic, not measurement; the per-line columns assume DDR5 and about 42 output tokens.

| Model class at Q4_K_M | Weights read per token | Generation, DDR5-5600 | Generation, DDR4-3200 | Per line, uncached 1,000-token frame | Per line, cached (~150 new tokens) |
|---|---|---|---|---|---|
| 4–4.5B dense-equivalent (Qwen3-4B-2507; Gemma 4 E4B slightly slower at ~2.7 GB) | ~2.5 GB | 17–25 tok/s | 11–16 tok/s | ~5–15 s | **~2.2–4.5 s** |
| 8B dense (Qwen3-8B) | ~5 GB | 9–13 tok/s | 6–8 tok/s | ~10–30 s | ~4.5–8.5 s |
| 3.3B-active MoE (Qwen3-30B-A3B-Instruct-2507) | ~2 GB | 18–28 tok/s | 12–18 tok/s | ~5.5–19 s | **~2.1–4.8 s** |
| ~1.5B-active MoE (LFM2-8B-A1B class) | ~0.9 GB | 40–70 tok/s | — | ~1.6–4 s | **~0.8–1.5 s** |

Two conclusions follow. First, only models with about 4.5B or fewer active parameters plausibly hit 2–3 s on this CPU, and **only if the prompt cache actually hits**. On DDR4 even a 4B is borderline. An 8B dense model misses by about 2× even in the best case, so Qwen3-8B belongs on the Modal L4 GPU fallback rather than on the CPU.

Second, and less obvious: whether the cache can be reused depends on architecture. A plain full-attention transformer can roll its KV cache back to any common prefix. Two kinds of layer cannot simply be truncated that way: sliding-window attention (Gemma 4, gpt-oss) and layers that carry recurrent state (Qwen3.5's Gated DeltaNet, Mamba hybrids, Liquid's convolution blocks). With those, llama.cpp can fall back to reprocessing the whole prompt unless checkpointing or full-size sliding-window caches are turned on. No source verified this behaviour for any candidate, which is why `tokens_cached` is a first-class bake-off metric below.

## Qwen3-4B-Instruct-2507 clears every constraint at once

Qwen3-4B-Instruct-2507, released 6 August 2025, is the summer refresh of Qwen3-4B. It has 4.0B dense parameters, a 262K native context and an Apache 2.0 licence, and it "supports only non-thinking mode and does not generate `<think></think>` blocks" ([HF model card](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507); [QwenLM/Qwen3 README](https://raw.githubusercontent.com/QwenLM/Qwen3/main/README.md)). The refresh transformed its writing scores. In Qwen's own evaluations it scores **83.5 on Creative Writing v3**, against 53.6 for the original Qwen3-4B in non-thinking mode, and 83.4 on WritingBench. That is within 1.5 points of GPT-4o-0327's 84.9 in the same table. The current shortlist pick, Qwen3-8B with thinking off, scores **64.5** on Creative Writing v3 in the Qwen3 technical report ([arXiv 2505.09388](https://arxiv.org/html/2505.09388)). The two sources used different evaluation versions (WritingBench even changed scale), so the gap is indicative rather than exact. Still, the direction holds across every writing metric Qwen publishes.

| Qwen-reported, non-thinking | Qwen3-8B (May 2025 report) | Qwen3-4B-Instruct-2507 | Qwen3-30B-A3B-Instruct-2507 |
|---|---|---|---|
| Creative Writing v3 | 64.5 | **83.5** | 86.0 |
| IFEval | 83.0 | 83.4 | 84.7 |
| Multi-IF | 69.2 | 69.0 | 67.9 |
| CPU decode class | 8B dense | 4B dense | 3.3B active |
| QLoRA on a free T4 | Yes | Yes | No (~17.5 GB) |

Sources: [arXiv 2505.09388](https://arxiv.org/html/2505.09388), [HF Qwen3-4B-Instruct-2507](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507), [HF Qwen3-30B-A3B-Instruct-2507](https://huggingface.co/Qwen/Qwen3-30B-A3B-Instruct-2507).

**The 2507 checkpoint also suits a strict output format, for a structural reason.** Qwen3-8B is a hybrid thinking model. With thinking disabled it still emits an empty `<think>\n\n</think>` block, and Ollama users have asked for it to be stripped ([ollama#10496](https://github.com/ollama/ollama/issues/10496)). An ICDM 2026 study found that when training labels contained an empty think block, LoRA-tuned Qwen models reproduced it in every prediction ([arXiv 2606.08051](https://arxiv.org/abs/2606.08051)). Identical training and serving templates keep that under control. A non-thinking-only checkpoint simply cannot fail this way: every output token is either the intensity label or the line.

**Training and export are the most routine of any candidate.** Unsloth says Qwen3-14B "fits comfortably" on a free 16 GB T4 ([Unsloth Qwen3 guide](https://unsloth.ai/docs/basics/qwen3-how-to-run-and-fine-tune)), and its general QLoRA minimums are 3.5 GB for 3B and 6 GB for 8B models ([Unsloth requirements](https://unsloth.ai/docs/get-started/fine-tuning-for-beginners/unsloth-requirements)). A 4B at 2,048 tokens therefore leaves room for batch sizes of 4–8. A rough compute estimate puts one epoch of 4,000 examples × 1,500 tokens at **about 2.5–4 hours on a T4 for a 4B, against 5–8 hours for an 8B**. Kaggle's weekly GPU quota is reported at about 30 hours ([paradox.engineer](https://www.paradox.engineer/resources/kaggle-free-gpu-tpu-compute)), so three 4B epochs fit in one week, while an 8B needs a run that checkpoints across several sessions.

The smaller model also leaves room for a higher-quality quantisation. On Llama-3.1-8B, Q4_K_M picked the same top token as full precision only 91.9% of the time, against 96.0% for Q5_K_M ([bshadmehr.me](https://bshadmehr.me/writing/quantization-q4-q8-explained/)). That is roughly two or three changed tokens per 30-token line, and any of them could be the intensity label or a player name. A 4B can afford Q5_K_M and still generate faster than an 8B at Q4_K_M. Qwen recommends a presence penalty of 0–2 on the 2507 models "to reduce endless repetition" ([HF model card](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507)), which matters for a model that reads its own previous lines.

**The honest case against a 4B is capacity, not fluency.** A bigger model is better at picking the key fact out of a 1,000-token frame, at not inventing a kill, and at varying its phrasing over hundreds of lines in a series. A 2026 study found LoRA-tuned 7B models beat 3B models at most LoRA ranks on a course Q&A task ([arXiv 2609.13918](https://arxiv.org/pdf/2609.13918)). In League of Legends data-to-commentary, the largest model tested, Llama-2-13B, scored best ([Liner review](https://liner.com/review/commentary-generation-from-data-records-multiplayer-strategy-esports-game)). The gaps are modest, though. In a 2026 extraction study, a LoRA-tuned Qwen3.5-4B reached **96.60% F1 against 96.95% for Llama-3.1-8B, at about 3.8× better throughput** ([arXiv 2606.08051](https://arxiv.org/abs/2606.08051)).

Evidence on grounding is thin for every candidate. Artificial Analysis gives Qwen3-4B-2507 an 84% hallucination rate, but that measures closed-book trivia recall, not faithfulness to a frame the model is given ([Artificial Analysis](https://artificialanalysis.ai/articles/qwen3-5-small-models)). No grounding benchmark covers models of these sizes. The planned entity validator and the code-computed facts (man counts, economy deltas) will do more for faithfulness than four billion extra parameters. And an 8B's better line is worth little if it arrives after the next kill.

## Gemma 4 E4B earns the comparison slot, now under Apache 2.0

Gemma 4 E4B (April 2026) stores 8B parameters but uses only 4.5B "effective" ones per token. Its per-layer embedding tables are looked up rather than multiplied, so it needs 8B-class RAM but only about 4.5B-class compute per token ([HF model card](https://huggingface.co/google/gemma-4-E4B-it); [Gemma 4 Technical Report](https://arxiv.org/html/2607.02770v1)). That puts it in the same speed class as the primary, which keeps the comparison fair. The project plan flagged Gemma's licence as "reportedly more restrictive than Apache 2.0". That was true of Gemma 1–3, but **Google moved Gemma 4 to Apache 2.0** ([Google blog](https://blog.google/innovation-and-ai/technology/developers-tools/gemma-4/); [Wikipedia: Gemma](https://en.wikipedia.org/wiki/Gemma_(language_model))), so the licence no longer separates the two candidates.

**Gemma's strength is prose.** On EQ-Bench Creative Writing v3, which is judged independently, Gemma models outscore same-size models from other families by wide margins. **Gemma 3 4B scores 13.91 on the rubric against 8.89 for Llama 3.1 8B**, and Gemma 4 12B reaches 15.71 ([benchmarklist](https://benchmarklist.com/benchmarks/creative_writing_v3/)). E4B itself is not on the board, so this is evidence about the family. It is backed only by second-hand reports that r/LocalLLaMA prefers E4B for creative writing ([Hacker News](https://news.ycombinator.com/item?id=48385906)). Qwen's prose evidence comes from Qwen itself, and Gemma's is independent but indirect, so only a head-to-head test will show which voice suits a hype line.

Format handling is clean: Gemma 4 has a native system role, and with thinking off the E-models emit no empty thought block ([HF model card](https://huggingface.co/google/gemma-4-E4B-it)). Tooling is first-class. llama.cpp and Ollama supported it from day one, ggml-org publishes official GGUFs, and Unsloth offers free notebooks and recommends E4B QLoRA as its small-model recipe ([Unsloth Gemma 4 guide](https://unsloth.ai/docs/models/gemma-4/train)).

**The risks are concrete.** E4B follows unusual instructions poorly: it scores 44.0 on IFBench, against 74.0 for the 12B, both measured in thinking mode ([Gemma 4 Technical Report](https://arxiv.org/html/2607.02770v1)). That matters less here, because one fixed output format is learned during fine-tuning.

Unsloth documents several quirks when training it on a T4 ([Unsloth Gemma 4 guide](https://unsloth.ai/docs/models/gemma-4/train)). Disabling the cache (`use_cache=False`) produced garbage logits, which Unsloth has fixed. A training loss of 13–15 is "perfectly normal". There is an fp16 overflow in the audio path on T4s. And the same page gives two contradictory VRAM figures, 10 GB and 17 GB. A text-only run with the vision and audio parts frozen should avoid the overflow, but check the VRAM fit in the first minutes of a Colab session.

The risk that could rule E4B out is in serving. It uses a 512-token sliding attention window and shares KV caches across layers ([HF model card](https://huggingface.co/google/gemma-4-E4B-it); [Gemma 4 Technical Report](https://arxiv.org/html/2607.02770v1)). If the llama.cpp server cannot roll that cache back to the common prefix, every line pays the full prompt cost, and E4B fails the latency bar however good its prose is. Its RAM footprint is no problem: 6.6–9.5 GB across the Ollama tags ([Ollama library](https://ollama.com/library/gemma4)), out of 32 GB.

**The newest Qwen models below 14B are still Qwen3.5 (March 2026).** Qwen3.6 and Qwen3.8 released nothing smaller than 27B, Qwen3.7 is API-only, and no Qwen4 weights had appeared as of late October ([QwenLM/Qwen3.8 GitHub](https://github.com/QwenLM/Qwen3.8); [Wikipedia: Qwen](https://en.wikipedia.org/wiki/Qwen); [Yotta Labs](https://www.yottalabs.ai/post/qwen-4-release-date-what-is-known-how-to-prepare-2026)). On paper Qwen3.5-9B is the smartest small model: IFEval 91.5, IFBench 64.5 ([HF Qwen3.5-9B](https://huggingface.co/Qwen/Qwen3.5-9B)), and the "most intelligent model under 10B" according to Artificial Analysis ([AA](https://artificialanalysis.ai/articles/qwen3-5-small-models)). It fails this project on three counts. For training, Unsloth says QLoRA "is not recommended" on any Qwen3.5 model, and bf16 LoRA on the 9B needs 22 GB ([Unsloth Qwen3.5 fine-tune](https://unsloth.ai/docs/models/qwen3.5/fine-tune)). For serving, Unsloth says no Qwen3.5 GGUF works in Ollama because the vision weights ship as separate files ([Unsloth Qwen3.5](https://unsloth.ai/docs/models/qwen3.5.md)), and an open issue reported Ollama running Qwen3.5 at a fraction of llama.cpp's speed ([ollama#14579](https://github.com/ollama/ollama/issues/14579)). For prompt caching, its Gated DeltaNet layers carry recurrent state, the hardest case for cache reuse. It also publishes no creative-writing scores.

**Qwen3-30B-A3B-Instruct-2507 is the most interesting stretch candidate.** It is non-thinking only, has the best Qwen-reported writing scores in range, and has only 3.3B active parameters, so it generates at roughly 4B speed ([HF model card](https://huggingface.co/Qwen/Qwen3-30B-A3B-Instruct-2507)). It breaks the training constraint, because Unsloth needs 17.5 GB to fine-tune Qwen3-30B-A3B ([Unsloth Qwen3 guide](https://unsloth.ai/docs/basics/qwen3-how-to-run-and-fine-tune)), more than a T4 has. At Q4 it also takes about 17–19 GB of the 32 GB of RAM, which is tight alongside CS2, a browser and OBS. But its GGUF can be speed-tested and few-shot-tested without any training, and a single short run on the Modal L4 would cover its QLoRA. So it enters the bake-off untrained and earns training time only by beating both 4B-class models.

gpt-oss-20b is the other small-active MoE, and the only one that fits a T4 for QLoRA (about 14 GB). It is rejected for four reasons. It "should only be used with the harmony format", and its reasoning effort goes down to low but never off ([HF gpt-oss-20b](https://huggingface.co/openai/gpt-oss-20b)). An aggregator puts its Creative Writing v3 Elo at 721.7, against 1034.5 for gpt-oss-120b ([benchmarklist](https://benchmarklist.com/benchmarks/creative_writing_v3/)). Unsloth's own tutorial contradicts itself on exporting to MXFP4 after training ([Unsloth gpt-oss tutorial](https://unsloth.ai/docs/models/gpt-oss-how-to-run-and-fine-tune/tutorial-how-to-fine-tune-gpt-oss)). And one unverified test found it leaving 54% of ordinary questions unanswered ([Sukhareva](https://msukhareva.substack.com/p/another-big-problem-of-gpt-oss-erratic)).

**The fastest candidates are hybrids that replace some attention layers with convolution or state-space layers.** LFM2.5-1.2B-Instruct is the speed floor. Liquid measured 2,975 tok/s prompt processing and 116 tok/s generation at Q4_0 on a Ryzen AI 9 HX 370 laptop CPU, against 2,008 and 62 for Qwen3-1.7B, with an IFEval of 86.2 ([Liquid LFM2.5](https://www.liquid.ai/blog/introducing-lfm2-5-the-next-generation-of-on-device-ai)). It "fits comfortably" on a free T4 ([Unsloth LFM2.5](https://unsloth.ai/docs/models/tutorials/lfm2.5.md)). LFM3-1.7B reports IFEval 96.7 and IFBench 73.0, ahead of Gemma 4 E4B in Liquid's own table ([Liquid LFM3](https://www.liquid.ai/blog/lfm3)). But it was five days old at research time, with no confirmed Unsloth, PEFT or mainline llama.cpp support and no licence stated in its launch post. All Liquid scores are measured by Liquid itself, and Liquid tunes for extraction and agent tasks at temperature 0.1. The LFM Open License is free below $10M revenue but adds conditions on top of Apache 2.0 ([LFM license](https://www.liquid.ai/lfm-license)).

NVIDIA's Nemotron 3 Nano 4B is the best-documented outsider. It is the only small model whose card reports reasoning-off IFEval (82.8), HaluEval (62.2) and EQ-Bench3 (63.2) together, and Unsloth says it fits a free Colab GPU ([HF Nemotron 3 Nano 4B](https://huggingface.co/nvidia/NVIDIA-Nemotron-3-Nano-4B-BF16); [Unsloth Nemotron 3](https://unsloth.ai/docs/models/nemotron-3)). Against it: its Mamba-2 layers raise open questions about both fp16 training on a T4 and prompt caching, its licence is custom, and at the same size it brings no writing advantage over the primary. These three models stay in reserve.

**The remaining families fall on age, tone, licence or size.** Granite 4.1 8B posts solid IBM-reported numbers under Apache 2.0 ([HF Granite 4.1 8B](https://huggingface.co/ibm-granite/granite-4.1-8b)), but at 8B it has Qwen3-8B's latency problem. Ministral 3 ships its Instruct weights in FP8, which a T4 cannot run natively; it also needs transformers v5 and has a "Le Chat" system prompt to override ([Unsloth Ministral 3](https://unsloth.ai/docs/models/ministral-3); [HF Ministral 3 8B](https://huggingface.co/mistralai/Ministral-3-8B-Instruct-2512)). Phi-4's own report admits "weak adherence to strict formatting requirements" ([Phi-4 Technical Report](https://arxiv.org/html/2412.08905)), Phi-4-mini scores IFEval 70.1 ([Phi-4-mini report](https://arxiv.org/pdf/2503.01743)), and no Phi-5 had shipped by August 2026 ([llmcheck](https://llmcheck.net/blog/phi-5-large-28b-review/)). Llama's licence forces any released fine-tune to carry a "Llama" name prefix ([Llama 3.2 licence](https://huggingface.co/meta-llama/Llama-3.2-3B-Instruct/blob/main/LICENSE.txt)), and Meta's Apache-licensed successor, Muse Glimmer, is a 30B dense model that needs 24 GB to train ([Unsloth Muse Glimmer](https://unsloth.ai/docs/models/muse-glimmer/train)). Olmo 3 7B Instruct trails Qwen3-8B on chat quality (AlpacaEval 2 LC 40.9 vs 49.8) in Ai2's own table ([Ai2 Olmo 3](https://allenai.org/blog/olmo3)). Two more fall on licence alone: Tencent's Hunyuan licence excludes the EU, UK and South Korea ([Hunyuan licence](https://huggingface.co/tencent/Hunyuan-1.8B-Instruct/commit/21ab9fd367ee99ba8001d34a182252ddb2ed255c)), and Cohere's Command R7B is non-commercial ([HF Command R7B](https://huggingface.co/CohereLabs/c4ai-command-r7b-12-2024)).

## A four-arm bake-off on stock GGUFs settles it before training

**Speed depends on architecture and quantisation, not on the fine-tune.** So the latency half of the decision can be settled now with off-the-shelf instruct GGUFs, before any training data exists. The few-shot baseline the project already plans can run on the same setup. Four arms cover the decision, and LFM2.5-1.2B is held back as the speed floor in case all of them fail.

| Arm | Role | Quants to benchmark | Fine-tuned? | Thinking control |
|---|---|---|---|---|
| Qwen3-4B-Instruct-2507 | Primary | Q4_K_M, Q5_K_M | Yes, free T4 | None needed |
| Gemma 4 E4B | Comparison | Q4_K_M, Q5_K_M | Yes, free T4 (check VRAM) | Leave `<\|think\|>` out of the system prompt |
| Qwen3-8B | Current pick; tests whether this machine can serve an 8B | Q4_K_M | Only if it passes stage 2 | `/no_think`; stop on `<think>` |
| Qwen3-30B-A3B-Instruct-2507 | Stretch: MoE quality at 4B speed? | Q4_K_M | Only on Modal L4, and only if it wins stages 2–3 | None needed |

The pass bars come from the budget. To keep the 95th-percentile (p95) latency at 3 s for a 35-token line whose new prompt section is 200 tokens, a model needs to **generate at about 18–20 tok/s or more** and **process the new section at about 200 tok/s or more**.

Thread placement matters on Intel's hybrid chips. A llama.cpp discussion found running on the P-cores only was about 3× faster than using all threads on 12th-gen Intel. That is 2023 data, from before many threading changes ([llama.cpp discussion #572](https://github.com/ggml-org/llama.cpp/discussions/572)). A later test found 12 threads 2.4% slower than 8 for generation ([InventiveHQ](https://inventivehq.com/blog/cpu-thread-scaling-llm-inference)). Prompt processing is limited by compute, so it may still gain from the E-cores. The llama.cpp server therefore takes separate thread counts: `-t` for generation and `-tb` for prompt processing ([llama.cpp server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)).

```bash
# Stage 0 (10 min): DDR4 or DDR5, and at what speed? This is a ~1.7x swing in generation speed.
sudo dmidecode -t memory | grep -E "^\s+(Type|Configured Memory Speed):" | sort | uniq -c

# Stage 1 (~1 h): raw speed. 192 = cached new section; 1024/1536 = cold full frame;
# 40-token generation; 8 threads = P-cores only.
for m in qwen3-4b-instruct-2507-Q4_K_M qwen3-4b-instruct-2507-Q5_K_M \
         gemma-4-E4B-it-Q4_K_M gemma-4-E4B-it-Q5_K_M \
         qwen3-8b-Q4_K_M qwen3-30b-a3b-instruct-2507-Q4_K_M; do
  llama-bench -m "$m.gguf" -p 192,1024,1536 -n 40 -t 8,16,24 -r 3 -o md >> bench.md
done

# Stage 2 (~2 h): prompt-cache behaviour under replayed match traffic.
# Take the best -t from the tg40 rows and the best -tb from the pp192 rows.
llama-server -m model.gguf -c 4096 -np 1 -t 8 -tb 16 --cache-prompt
# For each response, log tokens_cached, tokens_evaluated, and wall-clock time from send to last token.
# Gemma 4: if tokens_cached stays near zero, retry with the full-size sliding-window cache (--swa-full in recent builds).
```

| Stage | Metric | How | Pass bar |
|---|---|---|---|
| 0 | RAM type and speed | `dmidecode` | Decides which column of the latency table applies |
| 1 | tg40 (generation speed) at 8/16/24 threads | `llama-bench` | About 18 tok/s or more at the best thread count |
| 1 | pp192 / pp1024 / pp1536 (prompt speed) at 8/16/24 threads | `llama-bench` | pp192 about 200 tok/s or more; pp1536 gives the cold-start cost at the start of a round |
| 2 | Cache-hit ratio = `tokens_cached` ÷ prompt tokens | `llama-server` replaying 200+ consecutive frames in the real prompt layout | About 80% or more after each round's first frame |
| 2 | Time from event to last token, median and p95 | Replay wall clock, reported separately for in-round and buy-phase lines | Median ≤ 2.5 s and p95 ≤ 3 s on in-round lines |
| 2 | RAM in use | `top` during replay, with CS2, browser and OBS open | Leaves headroom; mainly a test for the 30B-A3B |
| 3 | Untuned few-shot quality | The planned baseline, same frames, all four arms | Sets the floor; also a refusal smoke test on "kill" and "headshot" |
| 4 | Format parse rate | GBNF grammar on the intensity token `calm\|engaged\|high\|peak`, plus a parser | 100% |
| 4 | Entity faithfulness | The planned validator: every name, weapon and number must appear in the frame | Compare arms; investigate any arm that does worse |
| 4 | Blind preference and repetition | Pairwise raters on held-out series; overlap with previous lines | The winner must also pass stage 2 |

The grammar matters because quantisation can flip the intensity token. No source tested any model on game-violence vocabulary, so stage 3 doubles as the refusal check. The planned replay tool supplies the traffic for stage 2.

**Read the results in order.** An arm whose cache-hit ratio stays near zero is out for CPU serving whatever its quality, so check Gemma first. If both 4B-class arms pass latency, fine-tune both on the free T4 with identical data splits and hyperparameters, rerun stage 2 on the fine-tuned GGUFs, and let blind preference and faithfulness decide; on a tie, pick the primary for its simpler tooling. If Qwen3-8B passes stage 2 on this machine, which is plausible only with DDR5 and high cache hits, it comes back as a third fine-tuned arm. If Qwen3-30B-A3B passes stage 2 and clearly wins the few-shot baseline, spend one short Modal L4 run on its QLoRA, since it is the only candidate that could raise quality without costing speed. If nothing passes, the choice is between the LFM2.5-1.2B speed floor on the CPU and Qwen3-8B on the Modal L4, and the few-shot baseline shows which compromise hurts less.

## Conclusion

The best base turns out to be an August 2025 checkpoint, partly because it is older. 2026's small-model innovations target long contexts and on-device memory: Gated DeltaNet in Qwen3.5, per-layer embeddings and sliding windows in Gemma 4, convolutions in LFM, Mamba-2 in Nemotron. A live caster on a CPU depends instead on something a plain full-attention transformer does trivially: rolling its cache back to a shared prefix. That makes prompt layout as important a decision as model choice. The match card and round state must come first and stay byte-identical between calls. Anything that slides, such as recent events and previous lines, must come at the very end. Otherwise every model on the list misses 3 s, the primary included.

The 2–3 s target should also be split in two. Kawamatsu et al. cut mean silence between utterances from 9.6 s to 0.3 s by generating the next line while the current one is spoken ([arXiv 2606.13322](https://arxiv.org/pdf/2606.13322)). Pipelining like that hides generation time for buy-phase analysis and calm lines, but not the gap between a clutch kill and the first word, which is exactly where the peak-intensity lines are. If the 4B meets the in-round p95, Qwen3-8B is not needed even on the GPU fallback. If it does not, the fix is a GPU, not a bigger CPU model. Finally, check Hugging Face again before training. Qwen4 was reported as imminent at the end of October with a 27B open-weight tier, and Qwen's newest large releases moved to custom licences ([Wikipedia: Qwen](https://en.wikipedia.org/wiki/Qwen)). Any sub-10B Qwen4 would need a licence check and a `tokens_cached` test before it could replace the primary.
